# @repo/i18n

Internationalization on [Paraglide JS](https://inlang.com/m/gerre34r/library-inlang-paraglideJs): messages live in `messages/{locale}/*.json`, the compiler turns them into tree-shakable typed functions, and components call `m.some_key()` like any other import. No extraction step, no Babel, and the same plain function call works in `.tsx`, `.tsrx`, and server code. The app ships `en`, `es`, and `fr`.

- `.` — re-exports from the generated runtime: `locales`, `Locale`, `isLocale`, `getLocale`, `setLocale`, `baseLocale`, and the `stet-locale` cookie constants.
- `./messages` — the compiled message functions, imported as `m`.
- `./server` — `paraglideMiddleware`, which pins each request's locale in AsyncLocalStorage.
- `./vite` — `paraglide()`, the Vite plugin that recompiles messages on edit, plus the shared compiler options.
- `messages/{locale}/{web,marketing,mail,common}.json` — the catalogs ([inlang message format](https://inlang.com/m/reootnfj/plugin-inlang-messageFormat)), split by surface and merged at compile time.
- `project.inlang/settings.json` — locales and message-format plugin config, including the `pathPattern` array that lists the three files.

Messages are split by surface (`web`, `mail`, and `common` for keys both call) purely to keep individual files small and reviewable; every key lives in one global namespace after compilation; regardless of which file defines it, any `m.*` call works from any surface. Add a fourth file by adding one entry to `pathPattern`. A key must not appear in two files: the plugin merges the list in order and a later file silently wins on collision, so a duplicate would just be confusing, not a compile error. A unit test guards against that.

The compiled output (`src/paraglide`, gitignored) is regenerated by the `prepare` script on every install and by the Vite plugin in dev, so fresh clones just work.

## Writing copy

Messages are keyed. Add the English text to the right surface file (`messages/en/web.json` for app UI, `messages/en/mail.json` for email, `messages/en/common.json` for the few keys both use), translate it in the `es` and `fr` equivalents, and call the generated function:

```tsx
import { m } from '@repo/i18n/messages';

function Example({ count }: { count: number }) {
  return <button aria-label={m.close()}>{m.items_count({ count })}</button>;
}
```

- The same call works everywhere: `.tsx`, `.tsrx`, hooks, module scope, and server code. On the server inside a request, `getLocale()` resolves from AsyncLocalStorage; in the browser, from the cookie.
- Parameters are typed: `m.people_with_access_to({ organizationName })` fails compilation if the placeholder set drifts from the message.
- Plurals use selectors in the message file (see `up_to_members` in `messages/en/web.json`); `Intl.PluralRules` picks the form per locale.
- Outside any request scope (queue consumers, Durable Objects, email) there is no ambient locale, so pass it per call: `m.reset_password_subject({ brandName }, { locale })`. When a whole render works in one locale (an email template), bind it once with `localized(locale)` from `@repo/i18n/localized` and call `t.reset_password_subject({ brandName })` — same types, no repeated `{ locale }`, no global state.
- Data-derived labels (plan names, notification types, roles) render through exhaustive `switch` maps in the UI, so adding a variant fails compilation until it has a translatable label.
- Sentences containing links are split into a text message and a link-text message (see the sign-in and sign-up footers). For rich text inside one message, [`@inlang/paraglide-js-react`](https://github.com/opral/paraglide-js/blob/main/docs/markup.md) offers `ParaglideMessage` with typed markup; nothing in the app needs it today.

Missing translations fall back to the English text at compile time, so a half-translated locale degrades gracefully. A unit test keeps every locale's merged key set identical.

## How the locale is chosen

1. A signed-in user's stored preference (`user.locale`, written by the Language card on the settings page through Better Auth `updateUser`).
2. The `stet-locale` cookie (pinned by `setLocale` when the user picks a language, re-pinned by the session context server fn on every load, and injected by the server entry when a signed-in request arrives without it, so a new device renders in the account's language immediately).
3. The browser's `Accept-Language` (Paraglide's `preferredLanguage` strategy).
4. `en`.

Steps 2 through 4 are Paraglide's strategy chain (`cookie`, `preferredLanguage`, `baseLocale`), configured once in `src/vite.ts`. On the server, `paraglideMiddleware` (wired in apps/web/src/server.ts) resolves the chain per request and isolates it in AsyncLocalStorage, so concurrent requests on the Worker cannot leak locales into each other. `<html lang>` reads `getLocale()`. Switching language calls `setLocale`, which pins the cookie and reloads.

Email picks the locale per recipient: mailer calls accept `locale` (the recipient's `user.locale` where known) and templates thread it into every message call. Invitees without accounts get the default locale.

## Adding a locale

1. Add the tag to `locales` in `project.inlang/settings.json`.
2. Create `messages/{tag}/web.json`, `mail.json`, and `common.json`, and translate them (below). The key-parity unit test fails until their merged keys match `en`'s.

The compiler regenerates `locales`, the `Locale` type, and every message function on the next dev-server start or `pnpm compile`. The settings page picker labels each language in itself via `Intl.DisplayNames`, so it needs no changes.

## Translating

The message files are flat JSON keyed by message id, so any translation tool or service works:

- **By hand or by prompt**: translate each value; placeholders like `{name}` and the plural selector structure must be preserved.
- **[Languine](https://languine.ai)**: JSON-first AI translation with incremental runs; point `languine.json` at `messages/en/*.json` with `es` and `fr` targets. Requires a Languine account.
- **[Lingo.dev CLI](https://lingo.dev)**: the same idea, with an `i18n.lock` for incremental runs. Requires a Lingo.dev account.
- **[Fink](https://fink.inlang.com)**: inlang's own web editor works directly on this project via `project.inlang`.

## Tests

```bash
pnpm test
```

Covers key parity across locales, `isLocale` narrowing, and per-locale rendering including plurals and parameterized mail subjects. The e2e suite (`apps/web/e2e/i18n.spec.ts`) exercises the settings switcher, persistence across reloads and cookie loss, and `Accept-Language` negotiation for anonymous visitors.
